# PARAKH Legal Metrology Compliance Engine

## 1. Purpose

The Compliance Engine is the legal/business-rule layer of PARAKH. Its purpose is to translate applicable packaged-commodity requirements into structured, testable validations.

It must be kept separate from OCR and AI models.

## 2. Legal Scope

The initial rule library is based on the **Legal Metrology Act, 2009** and the **Legal Metrology (Packaged Commodities) Rules, 2011**, together with applicable amendments and official requirements selected for the implementation.

The project must maintain a clear source/reference for every implemented rule and its version/effective period.

This repository must not treat an informal interpretation as authoritative law.

## 3. Rule Object

A rule should conceptually contain:

```json
{
  "rule_code": "LM-PC-EXAMPLE",
  "title": "Example requirement",
  "requirement": "Structured description",
  "applicability": {
    "category": "example"
  },
  "validation_type": "FIELD_PRESENT",
  "parameters": {},
  "source_reference": "official source",
  "version": "1.0",
  "effective_from": "YYYY-MM-DD"
}
```

The exact legal wording should be maintained in controlled rule documentation rather than generated by an LLM.

## 4. Rule Lifecycle

```text
Research / Official Source
          ↓
Legal/Domain Review
          ↓
Rule Definition
          ↓
Test Cases
          ↓
Versioned Rule Set
          ↓
Deployment
          ↓
Future Amendment
          ↓
New Rule Version
```

Historical inspection results should retain the rule version used at the time of evaluation.

## 5. Rule Categories

The prototype should represent applicable checks covering areas such as:

- Mandatory declarations
- Manufacturer/packer/importer information
- Net quantity
- MRP declarations
- Date-related declarations
- Consumer-care information
- Presentation/readability requirements
- Font-size-related requirements where measurable
- Other applicable packaged commodity requirements

The exact applicability and conditions must come from the official rule source used for the implementation.

## 6. Result Model

Every evaluation should produce a structured result:

```text
Rule
Actual value
Expected condition
Result
Evidence
Explanation
Rule version
Verification status
```

Supported result states:

- COMPLIANT
- POTENTIAL_NON_COMPLIANCE
- NEEDS_MANUAL_VERIFICATION
- NOT_APPLICABLE
- UNABLE_TO_DETERMINE

## 7. Deterministic Validation

Examples of deterministic checks include:

- Required field is present
- Numeric value can be parsed
- Date has an accepted structure
- Required declaration text is present
- Applicable category has required fields

Do not use an LLM to decide simple arithmetic or exact string/field conditions.

## 8. Uncertain Validation

Some package photographs cannot establish legal compliance with certainty. These should produce `NEEDS_MANUAL_VERIFICATION` instead of an invented binary result.

Examples include:

- Exact physical font size when no reliable scale/reference is available
- Ambiguous packaging placement
- Poor image quality
- Partially occluded declarations
- Context-dependent requirements

## 9. Evidence Requirement

Every potential violation should be traceable to:

1. Product/inspection
2. Applicable rule
3. Extracted field or observation
4. Source image/region
5. Explanation
6. Officer decision

## 10. Officer Decision

The officer should be able to:

- Confirm
- Reject
- Correct extracted information
- Request another image
- Mark for further review
- Add a note

The original AI extraction must remain auditable after correction.

## 11. Testing

Every rule should have test cases covering:

- Valid example
- Invalid example
- Missing data
- Ambiguous data
- Not-applicable case
- Boundary values where relevant

Rules should be unit-tested independently from the web interface.

## 12. Rule Updates

When a legal requirement changes, create a new version rather than silently changing the historical behavior of an existing rule.

The active rule set should be configurable by administrators with appropriate authorization.

## 13. Important Limitation

PARAKH is a decision-support and inspection-assistance system. Its output is not itself a legal finding. The enforcement authority and applicable official procedure remain authoritative.
